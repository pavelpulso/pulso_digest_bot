# YouTube как второй источник дайджеста

Дата: 2026-08-29

## Задача

Бот собирает посты из 39 Telegram-каналов и присылает утренний дайджест.
Нужен второй источник — видео из подписок на YouTube, чтобы в том же
утреннем сообщении была секция «что стоит посмотреть» за последние 7 дней.

Успех: в утреннем дайджесте появляется секция из трёх видео, отобранных по
релевантности читателю и по превышению просмотров над нормой канала;
показанное не повторяется; текстовая часть дайджеста не страдает, если
YouTube недоступен.

## Решение

Видео — это посты из источника `yt`. Они ложатся в существующую таблицу
`posts` и проходят через готовый конвейер: ранжирование, персонализацию по
👍/👎, «скрыть канал», дедупликацию, историю в `rankings`.

Отвергнутая альтернатива — отдельная подсистема со своей таблицей `videos`,
своим ранкингом и своей сборкой блоков. Она честнее по типам, но дублирует
конвейер, который уже написан и работает. Оправдана, только если видео
разойдутся с постами настолько, что общий конвейер начнёт мешать.

### Ключевой факт

SQLite хранит `"dQw4w9WgXcQ"` в колонке с INTEGER-аффинностью как текст, и
`UNIQUE(channel, post_id)` по такому значению работает. Проверено. Поэтому
строковый id видео кладётся в `posts.post_id` без миграции таблицы.

## Схема

### `posts` — две новые колонки

```sql
ALTER TABLE posts ADD COLUMN source TEXT NOT NULL DEFAULT 'tg';
ALTER TABLE posts ADD COLUMN duration_sec INTEGER;
```

Дефолт делает все 7 736 существующих строк телеграмными — миграция данных не
нужна.

Видео пишется так:

| Колонка | Значение |
|---|---|
| `source` | `'yt'` |
| `channel` | `yt:@handle` — читаемо в UI, работает со «скрыть канал» как есть |
| `post_id` | id видео (`dQw4w9WgXcQ`) |
| `text` | заголовок + описание |
| `link` | `https://www.youtube.com/watch?v=<id>` |
| `views` | просмотры, перезаписываются при каждом сборе |
| `duration_sec` | длительность в секундах |
| `date` | `publishedAt` |

Разделение источников идёт по колонке `source`, а не по префиксу
`channel LIKE 'yt:%'`: префикс — невидимый контракт, который развалится на
первом же имени канала с двоеточием.

### `channels` — две новые колонки

```sql
ALTER TABLE channels ADD COLUMN source TEXT NOT NULL DEFAULT 'tg';
ALTER TABLE channels ADD COLUMN external_id TEXT;
ALTER TABLE channels ADD COLUMN unsubscribed_at TEXT;
```

Для YouTube в `external_id` лежит id uploads-плейлиста, в `username` —
человекочитаемый `@handle`.

`getChannelUsernames()` начинает фильтровать `source = 'tg'` — иначе
телеграмный коллектор попытается читать YouTube-каналы.

### `digest_shown` — новая таблица

```sql
CREATE TABLE IF NOT EXISTS digest_shown (
  user_id INTEGER NOT NULL,
  post_id TEXT NOT NULL,
  shown_at TEXT DEFAULT (datetime('now')),
  PRIMARY KEY (user_id, post_id),
  FOREIGN KEY (user_id) REFERENCES users(user_id)
);
```

Единственная новая сущность. Без неё скользящее окно в 7 дней будет неделю
показывать один и тот же ролик.

### Существующие запросы

`getRankedPostIdsAboveScore`, `getRankedPostIdsWithTotal`,
`getPostsForCalendarDay` получают `AND p.source = 'tg'`. Видео отбираются
отдельной функцией со своим окном.

## Сбор

### Почему API, а не RSS

RSS-фид бесплатен, но отдаёт XML и не содержит просмотров — за метриками всё
равно нужен `videos.list`, а за списком подписок и вовсе OAuth. RSS не
избавляет от API, а добавляет второй формат данных и парсер XML.

Квота при 100 подписках (суточный лимит — 10 000 юнитов):

| Запрос | Когда | Юнитов |
|---|---|---|
| `subscriptions.list?mine=true` (по 50) | ежедневно | ~2 |
| `channels.list` батчами по 50 → uploads-плейлист | только для новых каналов | ~2 |
| `playlistItems.list` на канал | ежедневно | 100 |
| `videos.list` батчами по 50 | ежедневно | ~2 |

Итого ~106 юнитов в день. При 500 подписках — ~510, запас двадцатикратный.

### Импорт подписок

Подписки — приватные данные аккаунта, API-ключа для них недостаточно: нужен
OAuth. Ключ открывает только публичное (просмотры, длительности).

Отвергнутая альтернатива — разовая выгрузка Google Takeout и парсер CSV. Она
работает сразу и без Google Cloud, но требует ручной перевыгрузки при каждой
новой подписке — то трение, от которого фичи тихо умирают.

**Разовая настройка:** OAuth-клиент типа Desktop в Google Cloud, один consent
в браузере через `npm run auth:youtube`, полученный `refresh_token` ложится в
`.env` как `YOUTUBE_REFRESH_TOKEN`. Архитектурно это тот же паттерн, что уже
есть для Telegram: `src/auth.js` плюс сессия в `settings`.

**Ежедневно:** `subscriptions.list?mine=true` (1 юнит на 50 подписок, ~2 юнита
на несколько сотен) отдаёт актуальный список. Новые каналы добавляются в
`channels` с `source='yt'`, для них одним батчем `channels.list` достаётся
uploads-плейлист. Отписка проставляет `channels.unsubscribed_at` (ещё одна
колонка, NULL по умолчанию): канал перестаёт опрашиваться, но строка и его
прошлые видео остаются — они нужны для медианы и для `post_feedback`.

Access-токен живёт час и обновляется по refresh-токену перед сбором (~20
строк). Refresh-токен бессрочный, но отзывается сменой пароля Google — в этом
случае сбор видео падает с внятной ошибкой в лог и алертом админу, а
текстовый дайджест продолжает работать.

Дополнительно команда `/add_yt UC…` для точечного добавления канала, на
который нет подписки (например, собственного).

### Ежедневный сбор

Встраивается в существующий `cron-job.js --action=collect` сразу после
телеграмного:

1. `subscriptions.list?mine=true` — синхронизация списка каналов.
2. `playlistItems.list` по каждому каналу с `source='yt'`.
3. Отбор видео с `publishedAt` за последние 7 дней.
4. Один батч `videos.list` (по 50 id) на все новые — просмотры, лайки,
   `contentDetails.duration`.
5. Отсев шортсов: `duration <= 60s`. Стримы остаются.
6. `upsertPost` с `source='yt'`.

Просмотры перезаписываются при каждом сборе, поэтому у видео, вышедшего в
понедельник, к пятнице в базе актуальная цифра — на этом работает скользящее
окно.

Новый файл `src/youtube.js` по образцу `gramjs.js`: экспортирует
`collectYouTubeVideos()`, возвращающую `{ collected, errors, perChannel }` в
том же формате, что телеграмный коллектор. Принимает `baseUrl` в
конструкторе клиента — для тестов без сети.

В `.env` добавляются `YOUTUBE_CLIENT_ID`, `YOUTUBE_CLIENT_SECRET` и
`YOUTUBE_REFRESH_TOKEN`. Отдельный API-ключ не нужен: OAuth-токен работает и
для публичных запросов (`playlistItems.list`, `videos.list`).

## Скоринг

```
score = llm_relevance × (1 + boost)
boost = clamp(log10(views / median_channel_views), 0, 1)
```

**Норма канала** — медиана просмотров по его видео возрастом от 7 до 90
дней. Нижняя граница берёт только созревшие ролики, иначе медиана поедет
вниз от вчерашних.

**Boost считается только вверх.** Видео, вышедшее вчера, физически не успело
набрать просмотры. Если позволить метрике опускать скор, свежее всегда будет
проигрывать недельному и «топ за 7 дней» превратится в «топ прошлой недели».
Поэтому метрика умеет только поднимать: набрал десятикратно от нормы — удвоил
скор; не набрал — остаёшься при своём LLM-скоре и конкурируешь смыслом.

**Логарифм** не даёт миллионнику выжечь секцию: 50-кратное превышение
получает тот же потолок, что 10-кратное.

**Холодный старт.** Пока у канала меньше 5 созревших видео — `boost = 0`,
отбор идёт чисто по LLM. Через пару недель метрика включается сама.

**Отбор:** окно 7 дней назад от сегодня, минус записи в `digest_shown` для
этого пользователя, минус скрытые каналы. Из оставшегося — топ-3 по итоговому
скору.

Три, а не семь: видео стоит 10–40 минут внимания против 30 секунд на пост.
Семь роликов в день — заведомо непросматриваемый список, который приучает
пролистывать секцию целиком. Число меняется одной константой.

LLM-часть переиспользует `rankPosts` без изменений: заголовок и описание
приходят в том же поле `text`.

**Известное ограничение.** Медиана по 90 дням наказывает каналы, сменившие
формат: если канал перешёл с 5k на стабильные 50k, первые недели после смены
всё подряд будет выглядеть взлётом. Лечится сужением окна медианы — по факту,
а не заранее.

## Подача

Секция идёт последней — после текстовых блоков, перед кнопками оценки
дайджеста, с заголовком `📺 <b>Посмотреть</b>`.

Если свежих видео нет или все показаны, секция не отправляется вообще:
ежедневное «сегодня видео нет» — лишнее сообщение.

Блок видео повторяет структуру текстового, но со своей второй строкой:

```
🎬 Автор разбирает, почему архитектура на воркерах ломается под нагрузкой.

▶ @channel · 22 мин · 47k
```

Длительность и просмотры стоят рядом с каналом — это те два числа, по которым
принимается решение открывать.

Превью остаётся выключенным, как у постов: Telegram развернёт большую карточку
с обложкой, и три видео растянут секцию на два экрана.

Кнопки — те же `👍 / 👎 / 📌 Почему`. Фидбек идёт в тот же `post_feedback` и
учитывается в ранжировании наравне с постами.

Запись в `digest_shown` — после успешной отправки блока, а не при сборке:
иначе упавшая рассылка «съест» видео, которых пользователь не видел.

**Сознательно не делается:** отдельная оценка видео-секции, настройка её
размера, выключатель видео, кнопки «посмотреть позже». Каждое добавляется
позже одной строкой, если понадобится.

## Отказы

YouTube не имеет права ронять то, что уже работает. Три границы изоляции:

1. **Сбор** — `collectYouTubeVideos()` вызывается в своём `try/catch` после
   телеграмного. Упавший YouTube не мешает собранным постам попасть в базу.
2. **Дайджест** — сборка видео-секции обёрнута отдельно от текстовой. Не
   собрались видео — уходит обычный дайджест. Обратное тоже верно.
3. **Конфиг** — нет `YOUTUBE_REFRESH_TOKEN`, значит нет YouTube-каналов и
   коллектор не запускается. Без падений и без шума, по логике
   `OpenRouter: not ready`.

| Ситуация | Поведение |
|---|---|
| `403 quotaExceeded` | Не ретраить: квота суточная, повтор сожжёт остаток |
| `401` / отозванный refresh-токен | Сбор видео пропускается, ошибка в лог и алерт админу |
| Канал удалён / приватный (404) | Пропустить, записать в `errors`, продолжить |
| `videos.list` вернул не все id | Взять что пришло, недостающие подтянутся завтра |
| Видео без просмотров в ответе | `views = 0`, `boost = 0`, отбор по LLM |

Ошибки сбора попадают в тот же `perChannel`/`errors`, что телеграмные. Провал
утренней рассылки по-прежнему прилетает админу через `#reportDigestFailures`.

## Тестирование

`node --test` плюс `withServer` из `test/helpers.js` — фейковый HTTP-эндпоинт,
как в тестах AI-провайдеров. Сеть не нужна.

- **Синхронизация подписок** — новый канал появляется в `channels`, отписка
  помечается, но не удаляет прошлые видео, повторный прогон не плодит дублей.
- **Обновление токена** — истёкший access-токен обновляется по refresh перед
  сбором; отозванный refresh даёт внятную ошибку, а не молчаливый пропуск.
- **Парсер ISO-8601 длительности** — `PT59S` шортс, `PT1M` уже нет,
  `PT1H2M3S` считается верно. Пишется руками, зависимость не нужна.
- **Boost** — холодный старт при менее чем 5 созревших видео даёт 0;
  десятикратное превышение упирается в потолок 1; просмотры ниже нормы не
  уводят boost в минус.
- **Скользящее окно** — видео из `digest_shown` не приходит завтра.
- **Изоляция** — падение YouTube-коллектора оставляет телеграмные посты
  собранными; падение видео-секции оставляет текстовый дайджест отправленным.
- **Батчинг** — 120 id уходят тремя запросами `videos.list`, а не 120.

Реальный вызов Google API тестами не покрывается — проверяется живым прогоном
на проде.

## За рамками

- **Мульти-пользовательские квоты и подписки.** OAuth-токен и 10 000 юнитов —
  на одного пользователя. Второму понадобится свой consent и своя строка
  токена. `channels.added_by` уже есть, развязать по пользователям потом можно
  без ломки схемы.
- **Чистка старых постов.** 3 986 постов старше 90 дней не имеют ни фидбека,
  ни ранкинга и подлежат удалению — это ~4 МБ из 22 МБ базы. Отдельная задача
  после YouTube: сейчас удаление ничего не ускоряет, а историю просмотров,
  на которой стоит медиана канала, надо сперва накопить.
- **Баг онбординга.** `onboarding_completed = 1` выставляется при пустом
  `profile` — из-за этого два удалённых пользователя получали нерелевантный
  дайджест и ни разу его не открыли.
